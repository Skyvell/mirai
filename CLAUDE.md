# CLAUDE.md

Guidance for Claude Code (claude.ai/code) working in this repository.

## Product

**Mirai** — a direct-to-consumer precision-health app: individuals understand, track, and optimize their own biology from their own data. The loop is Measure → Interpret → Personalize → Intervene → Evaluate → Adjust.

**MVP scope is blood biomarkers only** (users upload lab PDFs; biomarkers tracked over time). Physiology (Oura/wearables), omics, interventions, and AI recommendations are product vision, not MVP. Not positioned as a medical device.

## Source of truth

`docs/` holds the decisions; code follows it, not the reverse.

- `docs/description.md` — product, personalization loop, full data model, long-term vision.
- `docs/stack.md` — frontend + backend stack, every choice tagged `[MVP]` (needed to ship) or `[LATER]` (add when a stated trigger hits). Consult before adding a dependency; respect the tags.

## Repo layout

Polyglot monorepo — each concern is a top-level sibling owning its own toolchain (no shared root package manager). Kept in one repo because the frontend generates its API client from the API's OpenAPI schema (an atomic contract) and infra deploys the API image. **Split trigger:** extract `infra/` into its own repo only when someone else owns infrastructure, or health-data compliance requires prod infra/state/secrets under separate access.

- `frontend/` — the web app (pnpm). Built.
- `api/` — FastAPI on Cloud Run (uv). Settings, Cloud SQL engine, Clerk JWT auth, health endpoints, and the first domain feature: lab-PDF upload → GCS → LLM parse → biomarker tables. Named `api/` (not `backend/`) to match the package `mirai_api`, image/service `mirai-api`, and runtime SA `mirai-api-run`; future `[LATER]` siblings (lakehouse, transformation) are also backend concerns.
- `infra/` — GCP infrastructure (OpenTofu). Cloud SQL + Cloud Run + a user-uploads GCS bucket + Secret Manager (Anthropic API key) + a Cloud Tasks queue (async lab parsing), for MVP.
- `[LATER]` per `stack.md`: DuckLake lakehouse + SQLMesh once omics/wearable scale demands it; direct lab/FHIR integration.

## Frontend

Run from `frontend/` (package manager **pnpm**):

```bash
pnpm dev      # Vite dev server (http://localhost:5173); regenerates the route tree
pnpm build    # tsc -b (typecheck) then vite build
pnpm lint     # oxlint
```

Stack: Vite 8 + React 19 + TypeScript, TanStack Router, TanStack Query, Tailwind v4, shadcn/ui (Radix + lucide-react, Geist font), generated API client (`@hey-api/openapi-ts`).

**Current state.** Nine routes: `/` (Overview), `/biomarkers`, `/sources` + `/sources/$uploadId/review`, `/settings`, and placeholders for `/wearables`, `/omics`, `/insights`, `/interventions`. Routes cover the full product vision; only biomarkers and lab uploads are in MVP scope.

**Feature slicing — read `docs/frontend_filestructure.md` before adding or moving a file; it is the source of truth and holds the full rules plus the rejected alternatives.** The one thing to know first: imports run one way, `lib/`/`components/` → `features/` → `routes/`, with `src/client/` a leaf importable by anything and edited by nothing. New feature = a directory under `features/` plus a thin route file.

**Routing — TanStack Router, file-based.** A file under `src/routes/` becomes a URL. The Vite plugin regenerates `src/routeTree.gen.ts` on dev/build — **never edit it by hand.** `__root.tsx` is the Clerk boundary only; the pathless `_authenticated.tsx` holds the profile gate and the nav shell, so every gated route lives under `routes/_authenticated/` while its URL keeps no `_authenticated` segment. Route files are config: `createFileRoute` plus `validateSearch`/`loader`/`beforeLoad`, rendering a feature page in one line. **A feature page never imports its route file** — it takes params and search as props, or uses `getRouteApi()`. `src/main.tsx` builds and mounts the router.

**Styling — Tailwind v4 + shadcn tokens.** `src/index.css` holds `@import "tailwindcss"` plus tokens. Real colors live in `:root` / `.dark` (`--background`, `--primary`, …); the `@theme inline` block maps them to Tailwind's color namespace so `bg-background`/`text-primary` work and dark-mode overrides resolve live. **Re-theme by editing `:root`/`.dark` values, not the `@theme` mapping.**

**shadcn/ui.** Components land in `src/components/ui/` via `pnpm dlx shadcn@latest add <name>`. `cn()` in `src/lib/utils.ts` merges class strings. The `@/*` → `src/*` alias is declared in both `vite.config.ts` and the tsconfigs (duplication is intentional: bundler vs. typechecker/shadcn CLI).

## API

Run from `api/` (package manager **uv**):

```bash
uv sync                                   # resolve deps + venv
uv run uvicorn mirai_api.main:app --reload
uv run pytest                             # router tests use fakes; no DB or network
uv run ruff check && uv run ruff format   # lint + format (config in pyproject.toml)
```

src-layout single package `mirai_api` (`src/mirai_api/`) — `api/` is the monorepo concern boundary (owns `pyproject.toml`, `Dockerfile`, `alembic/`, `scripts/`, `tests/`, `test_data/`), `mirai_api/` is the Python package identity; `src/` keeps the shipped package distinct from those siblings, which is the boundary the Dockerfile's dependency-caching layers rely on. Layered with domain-named files: `main.py` (app assembly + lifespan: logging config, engine warm-up), `core/` (`config` settings, `db` Cloud SQL engine, `security` Clerk JWT verify, `deps` FastAPI dependencies incl. service providers, `enums` shared vocabulary like `UploadStatus`), `models/` (SQLAlchemy, one file per model — singular, unlike the plural service/repository modules; `base.py` holds `Base` with the Alembic naming convention; `__init__.py` aggregates), `schemas/` (Pydantic API models, one module per router), `routers/` (`health`, `me`, `biomarkers`, `lab_uploads`), `services/` (`biomarkers` `BiomarkerService`, `lab_uploads` `LabUploadService`, `users` `UserService`, `lab_extraction` pure `map_extraction` + `catalogue_prompt`, no DB or I/O), `integrations/` (`storage` GCS, `tasks` Cloud Tasks enqueue, `lab_parsing` Pydantic AI agent + extraction schema), `repositories/` (`biomarkers` `BiomarkerRepository`, `biomarker_intervals` `BiomarkerIntervalRepository`, `lab_uploads` `LabUploadRepository`, `lab_results` `LabResultRepository`, `users` `UserRepository`), `seed/` (`biomarkers` + `biomarker_intervals` catalogue data, imported by the 0001 migration — it lives inside the package precisely so the migration can import it). New domain feature = model + schema + router + service + repository (thin layers where logic is trivial). Revisit module-per-domain packages when a second real domain (physiology) lands.

**`services/` vs `integrations/`.** `services/` holds domain application logic: classes taking repositories, shaped as domain exceptions → service class. **ORM → response schema mapping lives on the schema**, as a `from_*()` classmethod named for the source type minus whatever the class name already supplies (`BiomarkerMeasurementRead.from_measurement`, but `LabDraftItemRead.from_lab_result` since that class name doesn't state its source; derived arguments keyword-only). The test is whether the conversion does anything: **walks a relationship or aggregates rows → classmethod** (including the `RootModel` payloads, which own their own grouping via `from_measurements`/`from_intervals`); flat field-for-field where `ConfigDict(from_attributes=True)` suffices → call `model_validate` directly, since a classmethod that only forwards adds a layer. Domain-derived values are computed in the service and passed in (`_effective_status` is a timeout policy, so it stays there). Schemas may import models; **models never import schemas**, since one row feeds several representations and the innermost layer must not depend on the API boundary. A classmethod that walks a relationship says so in its docstring — `biomarker` is `lazy="raise"`, so the caller must have eager-loaded it. `integrations/` holds adapters over external systems (GCS, Cloud Tasks, Anthropic): module-level functions, no DI, no DB. The dependency runs one way — `services/` imports `integrations/`, never the reverse — and `integrations/` is where the external seams live that local runs and tests fake. `lab_parsing` is split along that line: the agent and its `LabExtraction` output contract are an integration, while `map_extraction` and `catalogue_prompt` — both pure — are `services/lab_extraction`. The catalogue is read per parse through `BiomarkerRepository.list_biomarkers` on the request session. **Never cache ORM instances process-wide** — a detached row binds to the first session that touches it, so a second concurrent parse fails; cache value objects if a hot path ever needs it. Relatedly, a writer holding only an id sets `biomarker_id`; a writer holding the loaded `Biomarker` assigns the relationship and lets the unit of work derive the FK. Reads attach the relationship via `joinedload`, which never replaces one already loaded — so a writer that sets the FK alone leaves a stale relationship behind.

**Tests** (`tests/`) mirror the source layers — `tests/routers/` (stub the service, exercise the endpoint) and `tests/services/` (fake the repositories, exercise the logic), each an `__init__.py` package because the two layers share test-file basenames. No unit test touches a DB or the network. `conftest.py` holds fixtures only; shared constants and doubles live in `tests/support.py`, which `pythonpath = ["tests"]` makes importable from either layer. Fakes are wired like the real objects they stand for — e.g. the lab-result fake resolves `LabResult.biomarker` from the biomarker fake it shares a "session" with, mirroring the real `joinedload`.

**Demo dataset (`test_data/` + `scripts/demo_data/`).** `test_data/biomarker_measurements.csv` is a committed synthetic series — one subject (male, born 1991-08-18), all ten markers, ~4-month cadence from birth to 2026-08-04, 1060 rows. Named `test_data/`, not `fixtures/`, because "fixture" already means a pytest fixture here; it sits outside `tests/` so the planned integration layer and the manual loader can both read it without either owning it. Its three-module toolchain is grouped in `scripts/demo_data/` (flat, imported via the script's own directory — hence `scripts/demo_data` in ruff's `src`). `generate.py` produces the CSV deterministically (fixed seed → byte-identical output, so regenerating and diffing is the drift check) and resolves each row's reference bounds from `seed/biomarker_intervals` rather than restating them; out-of-range values (~7%) are clustered into clinical episodes. `load.py --clerk-user-id <sub> [--replace]` (typer, dev-group dependency) loads it through `BiomarkerService`, the same validated path as the endpoint, and sets the subject's sex + date of birth since bands are stratified by both — the profile lives in `subject.py` because the stored bounds are only meaningful against it, and two declarations could silently disagree. Deliberately **not** migration-seeded: unlike `seed/`, this is per-user fake data, so it must not reach prod, needs a JIT-provisioned `users` row, and should be reloadable without a `downgrade base`. Sessions outside a request come from the `core/db.session_scope()` context manager, which `get_session` also routes through — services read relationships after commit, which only works with its `expire_on_commit=False`. The loader pairs it with `core/db.transaction()`, the same boundary a request gets, so `--replace` is one atomic delete-then-load. **A second subject is not a config change:** the pipeline is subject-agnostic, but the declaration tables are not — `EPISODES` holds absolute dates tied to this birth date (they would have to become age-relative), the `MARKERS` centers are tuned to male bands (HDL, hemoglobin, ferritin, creatinine), and `SEED` is single, so two subjects would share one noise path. Generalizing means a `Subject` registry plus a subject dimension on the `test_data/` path; cost is the same later as now, so it waits until a second subject has a stated purpose.

**Biomarker domain — endpoint → service → repository.** Routers stay thin (validate, resolve `CurrentUser`, delegate, map domain errors to `HTTPException`); `BiomarkerService` owns application logic and takes only its repositories; `BiomarkerRepository` owns DB access (flushes, never commits; plain ORM returns; queries scope by `user_id`). Service mutations take the subject `user_id` — the seam for future lab/admin actors (authorize actor-vs-subject in the service later; no roles now). Endpoints: `GET /biomarkers` (catalogue), `GET /biomarker-intervals` (canonical reference bands, slug-keyed), `GET /biomarker-series[/{slug}]` (per-user time series), `POST|PATCH|DELETE /biomarker-measurements` (bulk; DELETE takes `ids` query params). Ownership failures return 404 identical to nonexistent ids (no existence leak). All measurement writes — manual and lab-parse — go through `BiomarkerRepository.add_measurements`.

**Lab PDF upload → async parse → review → commit.** Extraction is error-prone, so LLM output never enters the record unreviewed; it lands as a draft the user confirms. `LabUploadService` (`lab_upload_repository` + `lab_result_repository` + `biomarker_repository` + `Session`) owns its own transaction boundaries — the one service that still commits, because the saga needs intermediate durability. Lifecycle (`core/enums.UploadStatus`): `queued → processing → awaiting_review → confirmed`, with `failed` terminal from `processing`.
- `POST /lab-uploads` (multipart, Clerk-authed, **202**) stores the PDF in GCS (`users/{user_id}/labs/{upload_id}.pdf`) as `queued`, then dispatches parsing: to Cloud Tasks when `tasks_enabled`, else in-request (local/dev). The worker `POST /internal/lab-uploads/{id}/parse` (OIDC-gated, not user-facing) claims the row via CAS (`queued→processing`, idempotent on redelivery), pulls the PDF from GCS, runs Claude (`claude-opus-4-8` via Pydantic AI), and writes `lab_results` (mapped + unmatched markers), reaching `awaiting_review`. A parse failure is terminal (`failed`); an infrastructure error resets to `queued` and re-raises so the queue retries. Stuck `queued`/`processing` rows older than ~10 min read as `failed` (no reaper) — what makes that safe is that `_resolve` is the service's **only** loader and applies `_effective_status` for every consumer — so `get` reports a stuck row as failed, `delete` allows removing it, and `submit` treats a stuck prior upload of the same bytes as failed so its file can be re-uploaded. Only `claim_for_processing` reads the stored status, in repository SQL, because that CAS *is* the state machine. Correspondingly `LabUploadRepository.list_by_content_sha256` is status-agnostic and unordered; the timeout policy stays in the service.
- `GET /lab-uploads/{id}` returns status + the nested draft (the `lab_results` awaiting review) while awaiting review; `PATCH /lab-uploads/{id}/draft` edits it (keep/drop rows, correct values, map an unmatched marker to a catalogue `slug`); `POST /lab-uploads/{id}/confirm` commits the kept, mapped rows into `biomarker_measurements` (via `BiomarkerRepository.add_measurements`) and flips to `confirmed` (idempotent; `lab_results` rows retained as audit). The biomarker series API reads only `biomarker_measurements`, so unconfirmed lab results never leak in.
- Blocking GCS/DB/parse work runs via `run_in_threadpool` (no async SQLAlchemy). `slug` is the LLM key; `loinc_code`+UCUM `canonical_unit` are for future FHIR; units stored verbatim, canonical conversion `[LATER]`.
- Settings: `GCS_BUCKET`, `GCP_PROJECT_ID` (keyless via ADC), `ANTHROPIC_API_KEY` (Secret Manager on Cloud Run; `api/.env` locally), `UPLOAD_ALLOWLIST` (comma-separated user UUIDs — LLM cost gate; empty allows all), and the async-parse group `TASKS_ENABLED`/`TASKS_QUEUE`/`TASKS_LOCATION`/`TASK_INVOKER_SA`/`WORKER_BASE_URL` (all tofu-set; empty `WORKER_BASE_URL` keeps parsing synchronous).

**Transactions — the request owns the boundary.** `core/db.transaction(session)` commits on success and rolls back on error; `get_session` wraps every request in it, so **services and repositories never commit** (repositories flush, for ids and for constraint errors that a service can still translate) and a route may compose several service calls as one atomic unit. Because the boundary sits inside the router's exit stack, rollback fires before the app's exception handlers, so domain errors keep their 404/409/422 *and* discard their writes. `DbSession` carries `Depends(get_session, scope="function")` for one reason only: under the default `"request"` scope the commit runs *after* the response is sent, so a failed commit would surface as a 200 — `tests/test_db.py` pins that. Two deliberate exceptions: `get_current_user`'s JIT upsert commits its own unit of work, so identity survives a rollback the endpoint causes; and the **lab parse saga** — `submit`/`process` need intermediate durability, so the five private methods they run through commit their own boundaries (the `LabUploadService` docstring says why each one). The review endpoints are on the request boundary like everything else. Because a commit lands everything pending on the session, a caller must not stage other writes around `submit`/`process`. Corollary of `autoflush=False`: **a method that mutates and then reads sees pre-mutation state in its own SELECT**, so it must either `flush()` or read through the instances it mutated. `update_draft` does the latter — it assigns `LabResult.biomarker`, and the response predicates on that relationship rather than on the not-yet-flushed FK. `test_me.py` stubs no service provider, so it drives the real boundary; `tests/test_db.py` covers what stubbed routes cannot reach.

**Cloud SQL:** SQLAlchemy engine via the Cloud SQL Python Connector with **IAM DB auth** (no password) in `core/db.py`. Same code path for public-IP-now and private-IP-later.

**Migrations — Alembic**, configured via `[tool.alembic]` in `pyproject.toml` (no `alembic.ini`); `alembic/env.py` reuses the app engine. Models are the schema source of truth: new table/column = model change + `uv run alembic revision --autogenerate -m "..."` + review. Applied by the `mirai-migrate` Cloud Run job, which CI executes before each service deploy — the API never runs DDL. Primary keys are client-generated UUIDv7 (`uuid.uuid7`, Python 3.14).

**Users — JIT provisioning.** No Clerk webhook: on the first authenticated request, `get_current_user` (`core/deps.py`) upserts a `users` row keyed on the Clerk `sub` (race-safe `ON CONFLICT DO NOTHING`) and returns the ORM `User`; the identity lookup itself is `UserRepository.get_user`, so nothing else redefines how a Clerk `sub` maps to a row. `GET /me` returns identity + profile — the router maps it with `MeResponse.from_user`, needing no service — and `PATCH /me` sets `sex`/`date_of_birth` via `UserService`. Clerk webhook is `[LATER]` per `docs/stack.md` (trigger: deletion cleanup once health data lands).

**Clerk:** JWTs verified against the public JWKS (`core/security.py`); no secret key needed for verification. `Dockerfile` builds with `uv sync --frozen`, copies `alembic/` (one image serves API + migration job), runs non-root, serves on `$PORT`.

## Infrastructure

`infra/opentofu/` — OpenTofu on GCP (`environments/<env>/ + modules/app/`; see `infra/opentofu/README.md`). **Two planes.** Bootstrap is three stateless scripts creating only what tofu can't: `infra/scripts/00_bootstrap_state.sh` (`just bootstrap-state <project>`) → state bucket (`tofu-state-<project>`); `infra/scripts/01_bootstrap_github_trust.sh` (`just bootstrap-trust <project> <owner/repo>`) → WIF pool + `ci-deployer` SA; `infra/scripts/02_bootstrap_db_owner.sh` (`just bootstrap-db <project>`, after first apply) → runtime SA owns the app database (superuser-only SQL; ownership covers all future DDL). OpenTofu owns everything declarative, all in a single `modules/app` module — APIs (`google_project_service`, incl. `storage` + `secretmanager`), Artifact Registry, runtime SA + IAM (`cloudsql.client`/`instanceUser`, `storage.objectUser` on the uploads bucket, `secretmanager.secretAccessor` on the API-key secret, `cloudtasks.enqueuer` + `serviceAccountUser` on itself for worker OIDC), Cloud SQL (Postgres 17, IAM auth), a `<project>-user-uploads` GCS bucket (`storage.tf`), the `anthropic-api-key` secret (`secrets.tf` — shape + placeholder version; the real value never enters code/state), a Cloud Tasks queue (`tasks.tf` — bounded retries + concurrency cap for LLM cost), Cloud Run v2 (service + `mirai-migrate` migration job). **Worker URL:** the parse worker's target is the service's own URL, computed from the deterministic `{service}-{project_number}.{region}.run.app` form (`modules/app/locals.tf`) rather than read back from the service resource (a self-reference cycle) — so a single apply wires it and async parsing is always on for a deployed env. **Manual step (not tofu-able):** seed the real Anthropic API key once per project after the first apply — `just seed-secret <project>` (prompts for the key); parsing fails until seeded. Each `environments/<env>/` is a self-contained root (its own `backend.tf` + inlined values in `main.tf`) that calls `modules/app` — one env per GCP project; state in GCS. `dev` is live, `prod` is a scaffold. The Cloud Run service and migration job are created with a placeholder image + `ignore_changes` on the image, so CI owns the running revision and tofu owns the shape. Cloud Run→Cloud SQL via built-in connector (public IP); private IP is additive later.

**CI/CD** — `.github/workflows/deploy.yml` on push to `main`: `_deploy-infrastructure.yml` (`just tofu-apply dev`) → `_deploy-app.yml` (build/push `mirai-api:<sha>`, execute the `mirai-migrate` job with the new image, then `deploy-cloudrun@v3` updating only the service image), plus `_deploy-frontend.yml` (build + `wrangler pages deploy` to Cloudflare Pages) running independently. Keyless GCP auth via WIF; GitHub Environment `dev` holds `GCP_WORKLOAD_IDENTITY_PROVIDER`, `GCP_SERVICE_ACCOUNT`, `GCP_PROJECT_ID`, `GCP_REGION`, plus `CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` for the frontend.

## Frontend wiring

**Clerk auth — wired.** `@clerk/react` (v6). `ClerkProvider` wraps the router in `main.tsx` (key from `VITE_CLERK_PUBLISHABLE_KEY`); `__root.tsx` is the auth boundary — `<Show when="signed-in">` renders `<Outlet/>`, `signed-out` renders `<SignIn/>`. `_authenticated.tsx` then gates on a complete profile (`sex` + `date_of_birth`, else `<Onboarding/>`) and renders the nav shell, so a future public route (a shared report, an OAuth callback) can sit outside both. Gating is component-tree, not `beforeLoad`: that needs `queryClient` in router context, deferred until a route wants `loader` prefetch. Overview (`features/overview/overview-page.tsx`) fetches the protected API `GET /me` via the generated client to confirm the token verifies. Build config (`VITE_API_URL`, `VITE_CLERK_PUBLISHABLE_KEY`) lives in the committed `frontend/.env` — both values are public, not secrets; a gitignored `.env.local` overrides it for a local API (`.env.local` > `.env`).

**Frontend hosting — Cloudflare Pages (Direct Upload).** The frontend is a static Vite SPA, deployed from CI via `_deploy-frontend.yml` (build with pnpm, upload `dist/` with `npx wrangler pages deploy`). Deliberately **not** the Cloudflare GitHub App: that would grant a third party write access to this auto-deploying repo. Instead CI holds a Cloudflare API token scoped to Pages (`CLOUDFLARE_API_TOKEN`/`CLOUDFLARE_ACCOUNT_ID` in the `dev` Environment) — Cloudflare gets no repo access. Build config comes from the committed `frontend/.env`. `public/_redirects` (`/* /index.html 200`) serves the SPA catch-all so client-side deep links don't 404. Backend CORS is an allow-list (`frontend_origins`, comma-separated) covering both `localhost:5173` and the Pages origin.

**API client — generated (`@hey-api/openapi-ts` + TanStack Query).** `pnpm generate:api` dumps the API's OpenAPI schema (`api/scripts/export_openapi.py` — importing the app has no side effects, no env needed) and regenerates `src/client/` (fetch client, typed SDK, `*Options()`/`*Mutation()` TanStack Query helpers keyed on the backend's `operation_id`s). Run it whenever the API contract changes; `src/client/` is committed (CI's frontend job is pnpm-only), the intermediate `openapi.json` is gitignored. The client configures itself at creation via hey-api's `runtimeConfigPath` → `createClientConfig` in `src/lib/api.ts` (`baseUrl` from `VITE_API_URL`, Clerk token via hey-api's `auth` — attached only to operations the spec marks Bearer-secured, `HTTPBearer` in `core/deps.py`); `ApiProvider` in `main.tsx` (inside `ClerkProvider`) just injects Clerk's render-scoped `getToken`. `QueryClientProvider` wraps the router; queries refetch only on explicit invalidation (`staleTime` 5 min, no focus refetch), except the Sources report list which polls (`refetchInterval`) while any upload is `queued`/`processing`. Features consume `currentUserOptions`, `listBiomarkersOptions`, `uploadLabMutation` (fire-and-forget: 202 → invalidates the upload list; parsing is async), the Sources list (`listLabUploadsOptions` + `deleteLabUploadMutation`), and the draft review route `/sources/$uploadId/review` (`getLabUploadOptions` + `updateLabDraftMutation` + `confirmLabUploadMutation`). **Cache-invalidation knowledge lives in the owning feature's `api.ts`, so no call site restates a query key** — `biomarkers/api.ts` owns `invalidateBiomarkerSeries`; `lab-uploads/api.ts` owns `invalidateLabUploads`/`invalidateAfterLabWrite` (a confirm or delete changes both the report list and the series, so it calls into biomarkers rather than restating its key). Call sites still choose *when* to invalidate, from an `onSuccess` or after an imperative `mutateAsync` pair. Polling constants (`IN_PROGRESS`, `POLL_MS`) and the status label/variant maps live in `lab-uploads/status.ts`, with the `refetchInterval` predicate at each of the two call sites. `apiErrorMessage` surfaces FastAPI's `detail` from thrown error bodies.

## Code
- Best coding practises.
